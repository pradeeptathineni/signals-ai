# Project intent

Use with [`core/engineering.md`](../core/engineering.md). This file makes project value the first design constraint.

## Define the value

- Name the people or systems served, the problem worth solving, and the observable outcome that makes the work useful.
- State non-goals and the smallest end-to-end experience that realizes the intended value.
- Prefer durable utility, trust, and learning over feature count, novelty, code volume, or visible activity.
- Preserve the project's character and reason for existing. Adopt a convention because it strengthens that purpose, not merely because it is common.

## Choose by consequence

- Prioritize correctness and safety, then completeness, clarity, usability, maintainability, and efficiency as the project requires.
- Favor the smallest coherent product surface that users can actually complete, operate, and understand.
- Spend complexity only where it buys material capability, reliability, interoperability, or reduced operating burden.
- Prefer fixes that remove recurring friction or risk. Add enhancements when evidence connects them to project value; decline speculative breadth.
- Keep decisions reversible while value or demand is uncertain. Stabilize interfaces only after their useful shape is understood.

## Represent reality

- Distinguish implemented, locally verified, externally observed, inferred, and planned behavior.
- Make public claims proportional to reproducible evidence. Never convert missing credentials, unavailable services, or an unrun check into a success claim.
- State meaningful limitations and tradeoffs where a user or maintainer will encounter them.
- Keep documentation, examples, release notes, and product behavior aligned.

A project succeeds by delivering its intended value credibly and sustainably, not by appearing more sophisticated than the problem requires.
